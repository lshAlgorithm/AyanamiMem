# Design

## The core bet

Most memory systems hide their state in a database. AyanamiMem makes the opposite bet: **everything is a plain file**, and the filesystem structure is the memory structure.

This means:
- You can open any memory in a text editor
- `git diff` shows exactly what changed and when
- Sharing a memory subtree means copying a directory
- The LLM navigates memories using its existing `read_file` tool — no new protocol

The cost is that you cannot do relational queries across memories. The benefit is that every property of the memory (structure, content, history, access control) maps directly to a property of the filesystem that every tool already understands.

---

## Why plain Markdown

We considered JSON, TOML, SQLite, and a custom binary format. We chose Markdown because:

1. **LLMs already speak it.** When we inject a `_summary.md` into a system prompt, it looks exactly the same as what the LLM generates. No format translation.
2. **Links are native.** `[Planning details](./01-planning/_summary.md)` is a valid Markdown link that renders in GitHub, Obsidian, VS Code, and every other viewer. The LLM can read it and understand it as a navigable reference.
3. **Frontmatter is established.** YAML `---` blocks are used by Jekyll, Hugo, Obsidian, and countless other tools. Metadata lives alongside content without a separate schema file.
4. **Human-editable.** A user can open `.memos/japan-trip/_summary.md` and correct a mistake. The next session picks up the correction automatically.

## Why the filesystem is the tree

The RAPTOR hierarchy maps perfectly to a directory tree:

```
japan-trip/                   ← depth-2 summary
  _summary.md                 ← "Japan trip: Kyoto, onsen, 3000 USD"
  01-planning-details/        ← depth-1 summary
    _summary.md               ← "Planning phase: destinations and budget"
    001-destinations.md       ← leaf (verbatim conversation)
    002-budget.md             ← leaf
  02-temples/                 ← depth-1 summary
    _summary.md               ← "Kyoto temple recommendations"
    003-temples.md            ← leaf
```

Containment in the filesystem = parent-child in the tree. No separate edge table needed. `ls -R` gives you the full tree. `tree` command gives you a pretty view.

The alternative was to encode parent-child as UUID edges in a JSON file. That requires a custom viewer to understand the structure. The filesystem structure is its own viewer.

---

## Why relative-path links instead of UUIDs

UUID-based edges (`- PARENT: 7c9e6679-7425-40de-944b-e07fc1f90ae7`) require a lookup table. If you move a file, the link breaks silently because nothing enforces consistency.

Relative path links (`[Planning](./01-planning/_summary.md)`) break loudly — a broken link in Markdown is visible in any viewer. They're also self-describing: the path tells you where the file is. The LLM can follow a path directly with `read_file`. No lookup needed.

The compactor ensures relative paths stay valid by writing them at creation time, never moving files after they've been placed.

## Why key-based search, not full-content search

We embed the `key` field of each node, not the full body. The key is a 5–15 word phrase generated by the LLM during summarisation: `"Japan trip: Kyoto temples, onsen, 3000 USD budget"`.

Keys are:
- **Short** → fast to embed, low dimensionality noise
- **Descriptive** → written by the LLM specifically to be searchable
- **Stable** → a summary key doesn't change when a child leaf is updated (only when the summariser re-runs)
- **Hierarchical** → a depth-2 key summarises more than a depth-1 key; search naturally finds the right level of abstraction

Full-content embedding would embed hundreds of tokens, most of which are filler, and return results at the wrong granularity. A user asking "what was my Japan budget?" should get the summary node, not the individual leaf where they mentioned 3000 USD.

---

## Why async compaction

Compaction calls the LLM (to generate summaries). An LLM call takes 1–5 seconds. We can't block the user on every message.

Instead:
1. Leaves go to `_fresh/` immediately (disk write, <10ms)
2. `_fresh/` is always included in context verbatim (the "fresh tail")
3. A background thread compacts when enough leaves accumulate
4. The LLM sees structured summaries once they're ready; until then, it sees raw leaves

The fresh tail count (default 32) means the most recent 32 conversations are always available in full, regardless of compaction state. Only older conversations need the summarised view.

---

## Why the LLM doesn't need a new tool

The agent's existing `read_file` tool is sufficient because:

1. **Context injection**: The assembler puts selected `_summary.md` content directly into the system prompt. This includes the `## Children` links.
2. **Progressive disclosure**: If the summary mentions `[Planning details](./01-planning/_summary.md)` and the LLM needs more detail, it calls `read_file("./01-planning/_summary.md")`.
3. **Natural stopping**: The LLM reads until it has enough information, then answers. Depth is bounded by the LLM's judgment, not by the system.

The alternative — a custom `read_memory(uuid)` tool — requires the LLM to extract a UUID from text, which is fragile. Reading a file at a relative path is something the LLM already does for code files, config files, and documentation.

---

## Why all-MiniLM-L6-v2 for local embeddings

- **384 dimensions**: small enough that a numpy array of 10,000 nodes fits in ~15MB of RAM
- **Fully cached on disk after first download**: no network latency on subsequent loads
- **Fast inference**: ~1ms per batch on CPU for short keys
- **No API call**: this is the core property — search never touches the network

For the LLM summarisation calls, we support any OpenAI-compatible endpoint (OpenRouter, local vLLM, LM Studio). The embedder always runs locally.

---

## What we deliberately did not build

**A query language.** You don't need SQL to find memories. The tree walk + cosine similarity covers 95% of retrieval needs. For the other 5%, `grep -r` across the `.md` files works fine.

**A GUI.** The filesystem is the GUI. Obsidian, VS Code, GitHub — they all render the tree correctly out of the box. We'd have to build something worse.

**A sync service.** Files sync via Dropbox, rsync, git, iCloud — choose your own. We don't need to reinvent file sync.

**Access control beyond session directories.** A session's memories are private because they're in a private directory. The OS enforces it. A grant is a symlink. Revocation is `rm symlink`. We don't need a permissions database.
